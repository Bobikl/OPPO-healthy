# 开发与变更规则

这些是项目采用的约束。公开资料提供原则，具体边界由本项目决定，见 [来源](SOURCES.md)。

## E01 先明确需求和验收

用户的功能描述或需求不清晰，无法确定目标、范围、期望行为或验收条件时，必须第一时间询问用户并讨论，说明具体歧义和需要明确的内容。澄清前不得自行猜测需求、静默选定一种业务解释或实施依赖该解释的改动；可继续不依赖该问题的检查。讨论结果写入变更记录，作为实现与验收依据。已明确需求内的常规技术细节由开发者判断。

说明触发条件、期望行为、异常/空数据行为、影响对象和可观察的通过条件。性能要求记录操作、冷热状态、数据规模与测量终点，不能只写“丝滑”“更快”。界面修改同时考虑日期选择、返回、旋转/重建与错误状态。

新功能必须有明确使用场景；存在更简单的方案时比较取舍。对破坏既有契约或明显扩大维护成本的提议，开发者有责任提出异议，并提供具体替代。用户可以在理解取舍后调整需求；讨论不得伪装为已经实施。

## E02 先评估影响，再修改

列出本次改动的所有者、调用者、状态/数据写入点、执行线程、失败传播和回退方式。修改公共层时检查全部消费者，至少覆盖正常、空态、失败、取消、旧回调及重入。

已有工作区包含大量未提交变化。基线固定本次开始时的状态，只统计之后的增删改；禁止将既有修改一并格式化、回退、提交或当作本次成果。

## E03 一批一个目标

功能、缺陷修复和重构可以在同一目标下协作，但不夹带无关清理。跨域改动先拆出接口/兼容点，再迁移消费者，再删除旧路径；每步系统仍可用。不要把修补一处 UI 与账号、协议、数据库和语言迁移绑成一次大改。

临时绕行只有在原因、影响、替代方案、退出条件和问题编号明确时才可采用。不能无限保留无所有者的 TODO，不能用多个特判掩盖共同状态模型的缺失。

## E04 在共同原因处修复

缺陷记录应包含：现象、最小复现、证据、根因或仍待确认的假设、其他消费者、修复位置及回归范围。优先修复共同所有者中的错误；数据适配器中保留必要的协议/指标差异。共用库不等于共用正确流程，接入前置条件也必须统一。

## E05 保持清晰与解耦

UI 不拥有账号凭证、数据库提交、蓝牙连接或后台任务。平台适配处理 Android/SDK/Root 能力；可纯计算的协议校验、时间范围和状态决策应易于隔离测试。

复杂逻辑使用可阅读的分支和有意义命名，注释解释约束与原因。不要继续把状态机、错误处理和多个动作压成难以审查的一行；也不为格式化历史文件扩大本次差异。接口只为当前确定的共享职责建立，不引入未使用的抽象和依赖。

## E06 数据与兼容优先

遵守 [契约](ARCHITECTURE.md)。缺失不是零；原始绝对腕温不是基准温差；缓存不是云确认。更改持久格式、字段单位、账号/设备范围、去重键或同步 ACK 前必须写兼容与迁移决策。

回退不是恢复旧 APK 就一定完成：新版本已写的数据也可能受影响。先验证旧版读取能力或提供安全的向前修复。禁止通过清空用户数据掩盖升级缺陷。

## E07 验证是变更的一部分

测试由行为与风险驱动，不用源码字符串命中代替行为测试，不用桩替身结果证明 Android 实际事务或真实云协议。修复必须有能区分修复前后的反例；公共层建立参数化消费者回归。

需要实机/网络但当前无法执行时，保存可执行入口和待验证项，状态为“实现/离线已验，运行验收待做”。不能宣称该行为已修复验收。文档和低影响可逆修改只做必要检查。

## E08 审查、交付和销项

自审必须检查设计、功能、并发、复杂度、测试有效性及所有消费者。独立评审缺失时明确说明，不伪造审批者或自动评审结果。高风险状态/存储/协议变更应准备可供用户或后续审阅者检查的具体决策与证据；没有新的执行边界时不反复询问授权。

交付时给出范围、实际检查、未执行项、产物与主要限制。只有相关验收已执行并有证据，才能将问题台账标为已验证；新版本号、文档写完或测试脚本编译成功均不构成销项。
