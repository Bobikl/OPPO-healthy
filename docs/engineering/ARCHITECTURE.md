# 当前架构、职责和契约

这是逻辑职责与增量整改边界，不声称当前已物理拆分模块。现有原生 Java 类主要在一个包中；已知耦合见领域台账。三层目标设计保留，见 [决策 0001](decisions/0001-incremental-governance.md)。

## 领域与所有者

| 领域 | 当前主要实现 | 应拥有的职责与禁止扩散的依赖 |
| --- | --- | --- |
| D00 工程/交付 | `build.ps1`、`tests/`、`tools/quality_gate.py` | 构建、证据、版本和门禁；不改变设备或业务状态来凑通过 |
| D01 健康展示 | `HealthPage`、各详情、`HealthUi`、`HealthPageTransition`、图表适配器 | 交互、展示状态及渲染；通过统一会话消费快照，不直接提交业务数据 |
| D02 健康本地数据 | `HealthDataManager`、`HealthMetricsStore`、`HealthArchive`、`OfficialHistoryStore` | 查询、归档、投影、缓存及提交协调；区分权威档案、导入副本和派生缓存 |
| D03 账号/云同步 | `HealthAccountStore`、`AccountSdk`、`CloudSyncEngine`、`CloudStore`、`CloudNativeProducer` | 会话、鉴权、版本/游标、outbox/ACK 与调度；对 UI 暴露状态和操作入口 |
| D04 蓝牙/通知接管 | `RfcommWearTransport`、`Oaf*`、`OfficialHealthMonitor`、监听/前台服务 | 连接所有权、协议边界、发送队列和让出策略；页面不自行另建连接 |
| D05 设置/恢复/Root | `RelayConfig`、`ListenerRecovery`、`Root*`、设置 Activity | 设置意图、权限核验、受限恢复和进程资源；先确认真实授权与实际状态 |
| D06 睡眠录音/分析 | `Snore*`、`Osa*`、睡眠监测服务/控件 | 长任务、录音文件、分析和取消；生命周期以实际任务所有者为准 |
| D07 依赖/隐私/官方复用 | 资源/SDK 闭包、Manifest、日志及导入/导出工具 | 版本、签名、权限、遥测和数据暴露边界；不把官方内部实现当作稳定公共 API |

依赖方向：UI → 会话/操作入口 → 数据/平台适配；共享纯状态和数据模型不反向依赖具体页面。当前 `HealthDataManager` 兼有导入协调与快照发布，是需要渐进拆清职责的现有实现，不能凭改类名宣称完成解耦。领域间通过明确的输入、状态、错误及提交契约协作。

## 必须保持的契约

- **C-ID 身份范围**：账号、设备、时区、会话/连接代次明确绑定。旧回调在提交和发布前复核，退出、切换或取消后不得污染新状态。
- **C-DATA 真实与单位**：缺失、零值、未评估、未加载分开。所有时间/温度/时长字段声明单位、时区和来源；不推算不存在的腕温基准或补造曲线。
- **C-WRITE 提交所有权**：同一逻辑数据有明确提交协调者；档案、云副本和 UI 缓存不能各自成为互相覆盖的权威。数据库/游标/范围发布与相关版本保持一致，迁移和跨库合并需单独验收。
- **C-ASYNC 有界与取消**：队列、消息、响应、记录数、重试和总时限有边界；取消不是只隐藏 UI。CPU、网络和文件操作不占主线程或长事务。不要用一个全局锁串行所有领域。
- **C-LIFE 生命周期**：页面退订自己的监听与计时器；已由服务/仓库接收的任务按自身所有权、取消和期限结束。Activity 销毁不应擅自停止独立蓝牙或删除原始文件。
- **C-UI 一致呈现**：选择意图、目标范围和已呈现快照明确区分；首次进入与连续切换使用相同范围/身份门禁。本地完整快照优先与后台校对为公共策略，由指标提供完整性条件。加载状态不挤动图表。
- **C-SYNC 同步与确认**：启用数据类型不等于立即执行；手动、充电、定时等触发遵守用户设置。上传、服务器确认、下载及本地合并分开记录；精确确认对应不可变修订，不用“请求发出”充当成功。
  身心日汇总的已核实单字段缺失可按[决策 0004](decisions/0004-mental-partial-confirmation.md)保存 PARTIAL；完整源保留、其他字段精确确认，缺失 HRV 不伪造。部分状态不当作完整成功或无限重试理由，官方结构的发送脏标记不承担完整确认语义。
- **C-PRIV 最小暴露**：凭证、通知正文、原始健康值及真实数据库不进入源码、日志、变更记录或一般报告。诊断输出优先类型、计数、日期、布尔与错误码；必要原始包依实际授权和保留范围管理。
- **C-ART 产物一致**：源码基线、构建版本、APK 哈希、安装包和测试证据可对应；下一构建号与当前交付号分开。历史脚本或旧 APK 的成功不能证明当前版本。

当前代码违反上述目标的部分由台账明确记录。引入新依赖边或改变所有者时先修改决策与消费者验证，不能以“规范已存在”为理由直接宣称架构已经符合。
