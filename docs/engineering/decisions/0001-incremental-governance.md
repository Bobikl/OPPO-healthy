# ADR-0001：先固定契约和验证，再分域渐进整改

状态：本轮采用的工程流程；日期：2026-10-24。记录人为本任务开发代理，自审；没有声称独立人员审批。

## 背景

当前原生实现包含 219 个同包 Java 源文件，健康展示分散在 9 类控制器中。共享数据和绘制库已经存在，但接入条件、状态模型与验证口径仍会分叉。工作区有大量已有修改，历史文档和测试脚本包含多个版本。

既有 04 三层架构设计提出 Flutter UI、Android 平台所有者和 Rust 数据核心；其文档明确是渐进迁移设计。本轮不改变该目标，也不把它当成当前已实施结构。

## 决策

建立仓库内规则、契约、变更记录、问题台账和可执行本地门禁；先审查工程验证和健康呈现，随后按身份/提交、同步、连接、设置恢复、监测及依赖的边界推进。

先确定唯一状态/数据所有者和公共行为，再迁移实现。当前 Java/原版 View/Compose 可通过会话/适配接口完成约束，未来迁移技术栈复用相同验收与契约。暂不批量换包、换语言、引入 DI 框架或全面重写全部页面。

## 比较与代价

- 立即整体重写：结构可重新规划，但会同时改变 UI、生命周期、平台协议与验证，当前证据不足以安全验收。
- 继续局部打补丁：短期快，但公共修复无法约束消费者，已出现血氧特判和日历漏接。
- 渐进整改：需维护过渡边界与台账；每批保持可运行、可验证、可解释，旧路径逐批收敛。

## 验收和后续变更条件

规范在 Git 中可见，执行入口能拒绝越界和失败，首批审查具备证据与未完成状态。后续涉及新的提交所有者、跨语言边界、数据库迁移或后台生命周期模型时，另写决策说明兼容、消费者迁移及回退，不隐式修改本决策。
